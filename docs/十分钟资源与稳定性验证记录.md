# 十分钟资源与稳定性验证记录

日期：2026-10-21。数据版本：petkit-v1.3-638f0e235a。

## 方法与边界

使用新建备份恢复副本，启动默认守护模式的API、UI和单个任务工作进程。BGE本地模型及5类账号的查询路径先完成预热，然后以4个闭环客户端持续发起任务600秒，最后等待所有在途任务结束。依次覆盖全局净销售额、区域净销售额、区域30天售后设备率、区域采购收货量和受限账号拒绝；逐个查询核对独立原始行Python结果。

这轮使用demo批准模板，没有调用付费模型。属于10分钟有界稳定性样本，没有执行小时或天级运行，不代表真实模型容量、通用500表问数覆盖或生产SLA。

用Windows自带GetProcessMemoryInfo、GetProcessHandleCount和GetProcessTimes读取三个真实子进程的RSS、进程提交内存、句柄数和累计CPU时间，不安装新依赖。采样器检查当前进程读数有效、无效PID必定报错，打开的进程句柄均在finally中关闭。逐秒样本独立写入resource_samples.jsonl；进程提交内存与RSS不同，不将二者混为物理内存占用。

预先设定增长停止阈值：相对预热后基线，worker/API/UI的RSS分别增长超过1536/512/256MB、任一进程句柄增长超过512、控制库及WAL/SHM合计增长超过512MB，即停止。数值错误、非预期HTTP、任务90秒未结束、就绪异常或工作进程重启也停止。这些是本轮保护阈值，不是产品资源配额或泄漏判定标准。

## 首次失败与复测

首次采用urllib逐请求新建连接的测试在约71.8秒提前停止，记录到一次HTTP请求超时：217个已接收任务全部完成并通过校验，另一次提交未能返回。不能据此确定是连接、响应阶段还是服务端原因，也不能把它报告为10分钟通过。

本次改为每线程复用HTTP/1.1连接，增加connect/send/response_headers/response_body/decode阶段诊断，不加入自动重试，不修改业务服务，也不改超时预算。所有先前报告保留在报告prior_runs列表中。负载阶段使用6个客户端连接，结束后全部关闭。

第二次确实跑满600秒，1881个任务全部核对通过；但最终主线程复用了闲置约10分钟的预热连接，发送收尾探针时出现ConnectionAbortedError，原脚本整体completed仍为false。随后客户端增加发送前按闲置4秒主动换连接，4项真实本地HTTP回归通过：活跃复用、闲置换连接、失败POST不重放、429及退避头保留。

单独收尾补验先确认旧服务已退出、队列已经为空、1881个结果持久存在，再启动该副本做探针验证。实际闲置6秒后主动换连接，探针成功，最后进程关闭；没有重新跑负载或改写原始报告。这是“负载阶段完成＋收尾单独补验”，不是修复后整套脚本一次跑通。第一轮短连接超时的根因仍未确定，不能反向宣称已解决服务端故障。
