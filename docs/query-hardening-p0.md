# 问数语义、有限纠错和澄清P0（2026-10-28）

## 范围与入口

企业入口仍为 `src.enterprise.api:create_app`、`src.enterprise.worker` 和 `src.enterprise.query.Query`。本次沿用StarRocks数据面和PostgreSQL控制面，不另建演示链路，不修改旧评测分数、不训练模型、不改变权限或放宽发布门禁。

## P0-1：可执行语义契约

`src.enterprise.metric_contracts.resolve` 集中现有7指标：净销售额、30天激活率、30天售后设备率、设备日离线率、工单数、收货数量、期末库存。契约包含单位、粒度、公式、时间归属、日历月边界、数据截止日、成熟观察窗、分母/零分母、输出别名、依赖表、业务批准状态；读取同一release的指标版本、表列与关系，并检查维度、单位、版本和未来月份。

SHA256同时绑定规则、发布元数据、批准关系及服务端编译模板。契约在首答、修复请求和最终结果中一致；不能把哈希当成业务审批或关系等价证明。原有AST列绑定、授权表和关联键白名单、成熟队列校验、批准SQL标准化结构比较及结果单位校验继续执行。

未给月份时，现有批准模板使用发布快照的全部观察记录；契约明确展示这个范围，不能声称是本月。给月份时使用自然月起点/排他终点，超出截止日的月份拒绝，截止日所在月标记为部分月。时区、源状态纳入、删除策略及财务政策仍须真实Owner签收。

净销售额编译模板暂沿用源快照中全部订单，退款截至快照日归原支付月、先按订单行汇总再LEFT JOIN。不能在没有源纳入政策审批时悄悄新增“已支付”筛选。当前合成源订单均为已支付；真实源必须在接入和发布前确认取消/退款订单政策。

## P0-2：有限纠错

最多2次生成（首答＋一次修复），不是worker重新领取，也不会无条件重放网络请求。两次生成累计使用 `settings.model_seconds`（默认45秒）；HTTP阶段超时取剩余预算，响应到达后再次检查累计耗时。HTTP库的阶段超时不是精确的端到端强制中止，也不能保证中断服务端已开始的推理。

SQL首次执行时建立共享截止时间，重试使用相同deadline，数据库query_timeout按剩余时间设置，并保留监控取消/KILL QUERY、内存、行数和字节上限。生成修复消耗这段已开始的SQL窗口，不会给第二次SQL重新分配完整15秒。

可修复：格式/完整JSON/plan缺失或截断；SQL语法和列绑定；确定性的StarRocks编译错误；批准语义偏差；结果别名/单位契约失败。修复反馈只有逻辑SQL、固定错误码及固定建议，不发送数据库原始错误、物理表名、连接信息、查询结果行或参考答案。

不修复：权限或指标切换、未批准关联、撤权、取消、租约丢失、网络/HTTP故障、模型和SQL超时、数据库断连、资源错误、强制复核不一致及未知异常。首答、修复、SQL执行和最终发布均继续受权限/租约检查约束。

每次尝试记录安全的结果/错误码，成功结果包含repair_count、累计模型耗时和metric_contract。两次仍失败返回 `status=error, error_code=SQL_REPAIR_EXHAUSTED`，SQL及result为空；不能计为问数成功，也不能冒充有效业务澄清。

## P0-3：澄清和能力边界

确定性意图在检索/模型/SQL前执行。`Clarify`携带reason、missing_slots、候选选项及是否需要Owner审批。宽泛“销售额/收入”不再默认为净销售额；“在线率”不能映射为离线率；退款率必须区分金额/订单/设备分母与归属；同比/环比需比较周期和对齐方式；累计/分层需起点、重置和边界；未知筛选/多个指标/多个维度不得忽略。

当前未新增退款率、同比、累计、采购未交付或分层的可执行指标。问清信息也不等于这些能力已自动启用，仍需Owner审批及新增编译/校验和独立回归。澄清结果无SQL和业务数据。原有同用户、授权、release和指标版本绑定的追问机制保留；不是自由拼接历史SQL。
