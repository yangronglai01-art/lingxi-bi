# 单机分档压测与短时持续负载记录

日期：2026-10-17。数据版本：petkit-v1.3-638f0e235a。

## 方式

在新建的备份恢复副本上启动默认守护模式的API、Streamlit及一个持久任务工作进程。使用现有本地BGE-M3检索和demo批准模板，不调用付费模型。500张物理表对应40张核心表和460张扩展表；本轮不是500种业务查询覆盖验证。

本轮使用闭环负载：每个客户端提交一个任务，轮询至终态后再提交下一题。1、4、8、16并发分别持续发起15秒，再以16并发持续60秒，停止发起后等待在途任务完成。请求分布覆盖全局分析、区域销售、区域售后、区域供应链和受限查看账号，前四类分别执行净销售额、净销售额、30天售后设备率和采购收货量，查看账号预期被拒绝。

每条成功结果均核对独立原始行Python计算结果，拒绝任务检查无结果；每秒采样运维就绪、队列和守护重启数。数值不一致、非预期HTTP状态、任务超过90秒、就绪异常或工作进程重启时停止升档。客户端每次HTTP超时15秒；常规轮询间隔0.25秒。

## 使用结论

这是当前单机、单工作进程、固定题型下的有界性能样本。若继续增加客户端后吞吐未增加而P95明显上升，应控制在途请求并保留队列背压；不应把客户端并发数当成并行SQL工作进程数。16并发能完成任务，不等于16并发是适合用户交互的默认值。

没有模拟指定到达率，也没有测开放系统的极限QPS；闭环会随延迟升高自动降低发起速率。60秒持续阶段属于短时稳定性验证，不能替代小时或天级运行、磁盘增长、长期资源泄漏与高可用测试。结果也不代表真实LLM服务吞吐、费用、生产SLA或实际企业500表业务覆盖。

本轮在途客户端上限16，小于单员工20和全局200的配额，因此未必触发429；若没有429，不把该结果当作本轮超载背压验收，历史配额验收记录另存。
