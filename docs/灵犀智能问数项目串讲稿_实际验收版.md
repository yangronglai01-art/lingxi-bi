# 灵犀智能问数项目串讲稿
## 项目开篇介绍
我做的是灵犀智能问数，一个面向智能宠物硬件业务场景的 Text to SQL 项目。我参考小佩网络科技（上海）有限公司所在的业务方向，自行构建了销售、设备、售后、库存和采购收货数据，用来验证从自然语言提问到受控查询的完整流程。当前已经完成单机模拟落地和有界验收，还没有接入这家公司的真实内部数据。
这个项目解决的是业务人员查数依赖人工写 SQL，同时指标口径和数据权限容易不一致的问题。用户可以询问各型号净销售额、售出 30 天激活率、售后设备率、设备日离线率、工单数量、当前库存和采购收货数量。系统会先判断口径与权限，再检索相关元数据，生成并检查 SQL，最后在受控范围内执行和返回结果。
我的主要工作覆盖模拟数仓、元数据与指标治理、混合检索、SQL 生成与校验、区域权限、持久任务、数据发布恢复和评测。项目从原来的少表全量 schema 输入，升级到 500 张物理表的检索供给。500 张表由 40 张核心表和 460 张合成扩展表组成，真实验证的业务能力集中在 7 个已登记指标，不能把表数量理解为 500 张表的所有业务都已覆盖。
## 项目整体流程
构建阶段，我先明确事实表粒度、主外键、批准的关联路径、字段描述、枚举和指标定义，再生成模拟数据。元数据与业务快照绑定版本，避免模型用新口径去查旧数据。当前活跃版本有 205397 行、3202 张订单，数据观察截止日固定为 2026 年 10 月 16 日。
查询阶段，前端携带持久身份提交问题；服务先做指标匹配、权限检查和歧义处理，再在授权表范围内检索。混合召回把 BM25 和本地 BGE M3 的结果用 RRF 融合，随后补齐指标依赖和批准关联路径。模型获得相关表字段、关系、指标口径与数据截止日，输出结构化计划和 SQL。
生成之后，服务做 SQL AST 白名单校验、有限的业务语义校验与结果契约检查。在执行连接中安装区域临时视图，再执行只读 DuckDB 查询。业务返回区分 success、denied、clarification、timeout 等状态。完整任务状态和审计写入 SQLite，用户可以查询历史任务与最终结果。
## 实际技术选型
后端是 Python 和 FastAPI，前端是 Streamlit，查询仓库使用 DuckDB，身份、任务与审计使用 SQLite。元数据保存为版本化 JSON；BGE M3 在本机 CPU 上编码，向量以本地矩阵文件保存。生成模型使用已有配置的 DeepSeek API。该版本没有部署 MySQL 元数据中心、Elasticsearch、Qdrant 或 LangGraph。
我选择这些组件，是为了先验证业务正确性、权限和恢复流程，减少单机模拟环境的运维负担。500 张表对应的检索向量只有 507 条、1024 维，这个体量用本地矩阵就能工作。向量库或分布式查询引擎是否必要，应根据后续的数据量、并发和运维需求决定。
## 从全量 schema 到检索供给
全量输入的问题是噪声和上下文预算。扩展到 500 张表后，即使上下文容得下，也不适合把所有字段交给模型自己选择。我把表名、说明、字段描述、枚举和指标依赖组织成检索文档，优先让问题与数据资产对齐。
BM25 路径覆盖表、字段和指标依赖文档；稠密路径对表级内容和指标文本编码，表文本中包含字段描述。当前不是每个字段独立做稠密向量。融合后的候选通常取前 8 张表，再补充批准关系和指标依赖，上下文最多 14 张表，并受字符预算限制。最终按选中表提供完整字段，这也意味着当前没有验证字段级独立排序能力。
检索必须先受权限约束。一个员工无权访问的表，不应先进入上下文再期待模型自行忽略。关系补全也只沿批准路径执行，不能因为两张表都有 device_id 就允许模型任意关联。
## 指标口径如何治理
目前治理了 7 个指标：净销售额、售出 30 天激活率、售出 30 天售后设备率、设备日离线率、工单数量、库存数量和采购收货数量。每个指标记录别名、定义、依赖表、粒度和版本，关键指标另有确定性语义与输出检查。
净销售额要先按订单行归并退款，再从销售金额中扣减，避免关联多笔退款放大销售行。售后设备率按设备去重，不能拿工单数替代设备数。库存需要按 SKU 和仓库取指定窗口内最新快照，不能跨日期直接求和。采购收货按收货事实的 quantity 求和，不能用订购量或收货单数替代。
30 天指标同时有两个时间条件。分母只包含截至观察日已经满 30 天的售出设备；分子只计算对应设备支付日起 0 至 30 天内的事件。未发生事件、晚激活和晚报修设备仍保留在分母。数据截止日固定后，运行日期变化不会悄悄改变样本成熟范围。
## SQL 生成与有界修复
模型输出 JSON，其中包含指标、维度、时间、过滤、关联、粒度和假设，以及 SQL。确定性规则先处理已知指标与明显歧义，模型负责基于受控上下文生成查询。模型模式失败不会悄悄回退成演示模板，避免把模板成功当成真实模型成功。
修复最多一次，一道题最多两次生成尝试，生成总预算为 45 秒，包含检索冷启动时间。错误信息与同一版本上下文返回给模型，要求修正。权限拒绝和关键歧义应返回明确状态，不能靠增加重试次数绕过。
当前没有上线多模型投票或无限多步推理。我优先把口径契约和错误分类做清楚，再根据真实失败样本决定是否引入更复杂的编排。
## SQL 安全与区域权限
安全不是只在提示词里写一句禁止修改数据。我使用 AST 校验，只接受批准的只读查询，检查表、列、函数和关联；限制外部文件、网络、系统表与不安全结构。执行连接同时关闭外部访问，不能仅靠语法检查作为唯一边界。
身份在 SQLite 中持久保存，包含角色、区域、策略版本和令牌哈希，支持禁用及轮换。检索、任务访问和执行都检查身份。销售与设备类区域归属沿订单和售出设备桥确定，库存与收货按仓库区域确定，不能用一个地区字段套所有事实表。
执行时，为每次连接安装受限区域临时视图，并阻止绕过视图直读原始限定表。这样即使模型漏写地区过滤，也仍由执行层限制数据。这是应用执行层的区域控制，尚不是数据库原生 RLS，也没有接入企业 SSO。
## 查询成本如何控制
单次 SQL 执行超时为 15 秒，DuckDB 连接限制 512 MB 内存和 2 个执行线程，单进程有 3 个查询执行槽。结果最多返回 1000 行，并设置 2000000 字节预算，超范围时提示缩小问题。
这些是单机应用边界，不能当作完整多租户资源隔离。当前默认只有一个持久任务工作进程；更多 HTTP 客户端主要增加排队，而不是自然增加模型和 SQL 的吞吐。
## 持久任务与故障恢复
我把任务从同步 HTTP 请求里分离出来。用户提交后得到任务编号，状态保存在 SQLite，客户端轮询或查询历史。员工最多 20 个待处理任务，全局最多 200 个；超过配额返回 429 和 Retry After，拒绝的提交不会变成隐藏任务。
幂等键绑定身份、问题、数据版本和策略。同一键重复提交返回同一任务，同一键换问题返回冲突。任务结果访问和取消都检查所有者，跨账号读取不能获得任务信息。
工作进程有租约和心跳，监督器对进程退出做有限重启。默认最多累计重启 3 次，再次失败停止本次拥有的进程。进程中断不会自动重放付费模型调用；取消也不代表已经发出的模型请求可以撤销计费。当前没有多实例高可用，也没有对所有活着但卡住的进程实现自动恢复。
## 如何模拟业务落地
我补了支付订单、出库、激活、退款、工单、采购和收货事件，让新增业务可以进入数仓，再通过受控发布成为可查询版本。当前已应用 25 个模拟来源事件，分 4 批，来源归档和落库业务行都做过核对。
出库验证的是同区域整单发货，没有实现拆单、跨区域调拨和完整预占。采购允许分批和多仓收货，但累计数量不能超过订购量；尚不包含质检、应付与采购退货。初始历史数据独立模拟，不能声称所有历史库存与物流流水都已逐笔闭合。
每次发布保存快照、清单、来源和代码指纹，使用预期父版本比较，避免并发发布覆盖。备份恢复在新目录演练，验证恢复后应用可用。备份不包含明文员工令牌和模型权重，仍需要部署时单独配置。
## 如何评测正确性
我把软件回归、业务问数评测、检索评测和负载测试分开。最新完整回归是 379 项通过，另有一条既有依赖弃用提示；这不等于 379 道自然语言问题。离线批准模板仍是 37 条，治理指标仍是 7 个。
扩展问数集有 28 道开发者编写并预先冻结的问题，包括 16 道真实模型数值题和 12 道权限或澄清题。数值题用原始行 Python 聚合作独立预期，区域预期也在原始行上独立筛选，不拿系统模板 SQL 当标准答案。12 道行为题不需要生成调用。
这些是开发评测，不是外部盲测，不能据此声称生产准确率达到 100%。我保留首次失败及复核记录；修复评分器或业务规则后另存结果，不把第一次成绩改成通过。检索消融的小样本中，各路径都能找到必需表，也不足以证明 BGE 优于 BM25。
## 一个实际发现并修复的业务问题
最近做真实模型并发验证时，四道任务都返回执行成功，但独立数值核对发现一题激活率不对。SQL 对订单加了成熟时间限制，却只用事件日期小于观察截止日筛选激活，漏掉了逐设备的支付后 30 天上限。
我先保留失败 SQL 和返回结果，再补充 AST 语义规则：聚合类 30 天查询直接读取事件表时，必须在支持的局部 WHERE 或 ON 中明确支付日起 0 至 30 天的窗口。模型应保留 cohort 的 paid_date，在 outcomes 中筛选分子，再左关联完整分母。无法确认的结构拒绝执行，进入有界修复。
这次新增了 11 项事件窗口回归，包括缺上界、缺下界、31 天窗口、恒真 OR 绕过和原失败查询的简化复现，完整回归随后 379 项通过。真实模型并发复测 8 道题也通过。这个校验支持有限 SQL 形态，仍不是任意 SQL 的业务等价证明。
## 实测稳定性与并发
本机模板模式实际连续运行 3600 秒，4 个闭环客户端完成 14134 个任务，其中成功查询 11308 次、预期拒绝 2826 次，没有异常；成功查询端到端 P95 为 1.2452 秒，成功吞吐约 3.14 次每秒。结束时队列为 0，工作进程重启为 0，测试子进程全部退出，原实例任务、版本指针和仓库核对一致。
工作进程工作集峰值约 1996 MB，结束时约 1574 MB，句柄从基线 313 到结束 306，没有触发增长阈值。工作集和提交内存需要分别观察，一小时通过不能证明长期完全没有泄漏。这个负载是固定问题的闭环模板模式，不能换算成真实模型的生产容量。
小时测试在本次事件窗口语义修复之前完成，原报告保存了当时的代码指纹。修复后重新跑了完整回归、8 道真实模型并发题和 5 分钟模板短连接诊断，尚未对修复后的代码再做整小时测试。两组证据应按各自版本理解。
真实模型另做了两层验证：4 个 HTTP 客户端同时提交，默认单工作进程处理，四题全部通过，总用时约 27.35 秒；另用两批各 2 路直接服务调用验证适配器，四题全部通过，实测生成调用峰值为 2，直接阶段共 4 次生成。后者是受控实验，没有把线上工作进程改为两个，也不证明供应商内部并行能力或生产 SLA。
## 网络异常如何处理
曾有一次短连接负载在约 72 秒出现 urllib 超时，当时没有记录具体阶段。取证确认已确认接收的 217 个任务均持久化，重建时间窗内未发现额外任务；系统日志没有对应网络告警，但不能因此排除网络故障。
我补了连接、发送、响应头、响应体和解码阶段记录，不采集密钥与请求正文，也不自动重试掩盖失败。新一轮原始短连接方案运行 5 分钟，1379 个任务全部符合预期，未复现故障。因此首次短连接超时根因仍未确认。
另一次收尾失败是复用长时间闲置的旧连接，已通过发送前主动更换闲置连接处理，并有相关回归和完整持续测试验证。它和首次短连接超时是两条独立记录，不能合并成一个已经完全修复的问题。
## 面试常见追问
### 为什么 500 张表不用全部注入
因为模型需要的是当前问题相关且经过治理的上下文。检索缩小范围，指标依赖和批准关系保证完整性，字符预算限制噪声。扩展表用于验证大目录检索与隔离，核心业务能力仍按已验证指标说明。
### 为什么没有直接用向量数据库
当前只有 507 条稠密向量，本地矩阵能满足模拟环境。是否换向量数据库，要看动态更新、共享索引、服务化和检索规模，不能只因为有 500 张表就默认需要分布式组件。
### SQL 执行成功为什么还会算错
执行成功只能说明语法、类型和资源等条件满足，不能证明分子、分母、事件窗口和关联粒度正确。这次晚激活计入分子的案例就是实际证据，所以需要指标契约和独立数值核对。
### 如何防止关联放大
先明确事实粒度，再按业务键聚合一对多来源，例如退款先按订单行、工单先按设备归并。关联只能使用已批准关系，关键口径增加专门约束，同时在评测中构造多退款、多工单和缺失事件等数据验证。
### 为什么还保留演示模板
模板给确定性业务回归和稳定性负载提供基线，可以隔离网络与模型波动。真实模型路径单独验证且不静默回退，两个模式的成绩分开记录。
### 怎样描述个人贡献和项目效果
我可以具体讲清自己完成的模拟数仓、检索、口径、权限、任务恢复、发布和评测，并展示代码与原始报告。效果用已测样本、耗时和资源数据说明，不虚构真实企业任职、团队人数、上线用户数或业务收益。
### 距离真实企业上线还差什么
下一步需要和实际数据负责人确认源表映射及指标口径，接入企业身份与权限体系，确定数据出口策略、运行资源和运维责任，再做目标负载下的安全、稳定性与恢复验收。多实例高可用、长期监控和更多跨域复杂问题，也需要在真实环境另行验证。
