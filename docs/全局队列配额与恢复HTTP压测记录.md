# 全局队列配额与恢复HTTP压测记录

日期：2026-10-17。版本：petkit-v1.3-638f0e235a。

在新建的备份恢复副本中，直接写入16个临时分析员身份及token哈希作为测试夹具，凭据只在测试进程内存中保留；不修改原实例的5个员工身份。临时用户的创建并不算业务账号管理流程的验收。

启动默认守护的API、UI及单工作进程，预热后用32个HTTP客户端突发提交320次净销售额查询。每个临时账号只发20次，避免触发员工配额，隔离验证全局200个待处理任务的上限。后台工作进程全程正常消费，不人为暂停。执行demo批准模板及本地BGE，不调用付费模型。

| 突发请求 | 320次，32客户端 |

累计接收数可以超过200，因为突发发起期间后台同时完成任务；200约束任意时刻queued＋running，而不是历史接收总量。每0.05秒采样全局及每员工的待处理数，没有观察到越界；采样无法排除所有瞬时变化，事务配额边界的既有回归另存。

每个被接收任务均使用原始行Python聚合的净销售额逐组核对。所有拒绝响应都验证错误码、全局scope和退避提示。跨账号检查针对本轮真实HTTP任务进行，证明他人不能读取或取消该任务；不代表完成全部企业权限场景的验证。

结束后全局队列排空、运维就绪、所有测试子进程关闭。原实例员工身份及凭据摘要、任务记录、版本指针和业务仓库保持一致；恢复副本业务仓库未变。创建备份会在原库追加备份审计，因此不宣称原控制库完全没有写入。

本轮新增验收资产，没有变更业务实现；354仍为上一轮完整回归结果，不将本轮请求数加入软件测试条数。每次复测接收/拒绝数量可随消费速度变化，不要求固定计数，要求实际出现全局429且全局/员工采样待处理不超过200/20、拒绝不落库、结果正确并恢复。

本轮覆盖单机全局队列饱和与恢复，不证明真实模型吞吐、多实例一致性、长期稳定性或生产SLA。跨账号请求集中在同一指标，也不能当作500表问数覆盖率。
