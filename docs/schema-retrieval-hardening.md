# 企业问数：表结构检索与上下文组织（2026-10-28）

## 正式链路

入口仍为 `src.enterprise.query.Query`。流程：固定release和主体授权 → 仅可见目录BM25候选 → 如已配置则调用固定revision BGE → 去重RRF → 必需指标依赖与批准桥表 → 有界可选候选 → 真实请求序列化预算 → 冻结上下文 → 首答及一次修复使用同一快照 → 既有AST/语义/执行校验。

`src.enterprise.schema_context`负责选表、批准路径及预算；`prompt_context`负责与生成器共用的消息序列化。未改变旧同步演示检索器，没有新建旁路，不修改已有7指标、复杂口径边界或380题/22题成绩。

## 选表与权限

1. 先将角色允许表与当前scope的物理映射取交集。BM25索引只包含这个集合及依赖完全可见的指标，隐藏schema和隐藏指标描述不参与索引统计或证据。
2. BM25和BGE各最多24个候选；每条路线先授权过滤和去重，再以1/(60+rank)做RRF，同分按逻辑表名稳定排序。没有实际BGE时标记BM25，不能声称语义召回。已配置BGE但服务失败或索引不完整时终止，不静默回退。
3. 指标全部必需依赖优先。依赖之间若缺桥表，仅沿approved=true、关联键真实存在、主体可见的关系做最多4跳的有界最短路径补全。没有路径、字段漂移、必需依赖及桥表超过14张时澄清，不以截断掩盖缺表。路径补全不证明SQL关系等价或关联后不会倍增；原粒度/语义校验继续执行。
4. 最多接受2个可选候选锚点及其必要桥表，仍受14表和消息预算限制；断开的、超预算的候选逐项记录舍弃原因。不会把全部邻居塞给模型。

## 字段和上下文预算

- 保留被选表的全部字段名、类型、枚举和列元数据，不根据关键词盲剪分母字段或JOIN键；表粒度完整保留。只压缩表/列说明长度和别名，去掉模型不需要的表级源展示信息。元数据与用户问题始终视为不可信数据，不改变系统规则。
- 使用生成器同一序列化函数测量“问题＋元数据＋执行契约”，受配置上限和底座32,000字符上限共同约束，提前为一次修复预留8,000字符。字符预算不是token计数，`tokenizer_measured=false`；真实token余量仍须配合模型tokenizer测量。
- 必需上下文超限时明确要求缩小范围或登记汇总视图，不能删掉关键枚举、字段或指标规则来凑数。可选候选按整体路径接受或舍弃，不能保留两端而丢桥表。
- 首答与修复不重新检索、不切换release、不重新裁剪schema。失败SQL的完整修复对象太长时，整条省略并标记原因，只保留固定错误反馈；不会给模型截断到一半的SQL。

## BGE与观测

向量文档格式保持原样，没有改动已有向量内容哈希或触发自动重建。查询候选深度扩到24；查询时检查内容hash、revision、授权集合完整性、1024维、有限非布尔数值和单位范数。索引损坏、NaN、零向量或非归一化向量失败关闭。

响应context记录原始BM25/BGE候选、RRF分数和来源排名、selected/mandatory表、选表原因、舍弃原因、表列数量、消息字符数、修复预留及上下文hash。`scripts/score_enterprise_retrieval.py`分别统计BM25@8/@24、BGE@24、融合召回、最终覆盖率、上下文精度和强制补全数量；缺失或重复首答记录拒绝评分。没用BGE时BGE指标为null。
