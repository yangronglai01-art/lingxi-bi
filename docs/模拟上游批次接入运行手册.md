# 模拟上游批次接入运行手册

2026-10-17。当前数据版本：`petkit-v1.3-24708285df`；500表、3200订单、205,351行自建模拟数据。

## 本轮接入结果

通过模拟统一业务网关批次，接入3条退款、3条首次激活、3条工单创建，共9个事件。退款位于R1订单，新增退款合计30.00元，净销售额相应减少30.00元；激活与工单属于R2售出设备。激活同时生成绑定关系，工单同时生成创建状态与客服接触记录，共增加18行，仍为500张物理表。

这不是已经连接小佩接口。当前是本机UTF-8 JSON文件批次入口，日期限制在固定观察截止日2026-10-16内，支持历史补录。未实现通用CDC、新订单接入、工单状态流转、冲正/删除和实时设备日遥测。首次激活事件不会自动编造后续设备日在线数据。

## 协议

机器可读协议见[JSON Schema](模拟上游批次协议.schema.json)。金额固定为人民币元，必须使用正数、两位小数字符串。未知字段、未知事件种类、批次内重复event_id、无效标识、日期或金额不合法均拒绝。

```json
{
  "version": 1,
  "source": "simulated_gateway",
  "batch_id": "example-batch-001",
  "events": [
    {
      "event_id": "example-refund-001",
      "kind": "refund.created",
      "refund_id": "EXAMPLE-RF-001",
      "item_id": "EXISTING-ITEM-ID",
      "refund_date": "2026-09-15",
      "amount": "10.00"
    }
  ]
}
```

示例中的业务ID必须替换成确实存在的模拟业务ID，并满足日期和剩余退款额度；示例只是格式，不能直接视为合法业务批次。

支持事件：

| kind | 额外必填字段 | 实际写入 |
|---|---|---|
| refund.created | refund_id、item_id、refund_date、amount | 退款 |
| device.activated | device_id、activation_date | 首次激活、订单客户对应的首次绑定 |
| ticket.created | ticket_id、device_id、fault_id、employee_id、created_date | 工单、已创建状态、客服接触 |

外层source和batch_id只允许1到64位字母、数字、下划线、连字符；业务ID/event_id最长96位，允许字母数字及下划线、点、冒号、连字符。每批1到1000事件，文件最大2MB；超过大小限制在读取和落库前拒绝，不归档超限文件。

## 操作流程

```powershell
cd D:\projects\lingxi
.\.venv\Scripts\python.exe scripts/ingest_upstream.py ingest --file '你的模拟批次.json'
# 保存返回的candidate、parent；接入只生成候选，不直接改变业务数据
.\.venv\Scripts\python.exe scripts/manage_releases.py validate --generation 'candidate'
.\.venv\Scripts\python.exe scripts/manage_releases.py activate --generation 'candidate' --expected-current 'parent'
.\.venv\Scripts\python.exe scripts/ingest_upstream.py list
```

当前已经发布的样例批次在 `D:\projects\lingxi\data\petkit500\ingestion\inbox\landing-d5edff4af6.json`。再次向当前版本投递原文件会返回already_applied、applied=0，不重复记账。

返回staged仅表示候选已生成；不代表业务数据已发布。验证或发布失败后需检查原因，不能把接收成功当作上线成功。接入和发布由受信任的本机运维账号执行，业务员工不能通过API提交服务器文件路径。全局分析账号可经GET /ops/ingestion查看最近接入状态，区域账号拒绝访问该监控入口。

## 幂等与分支

批次身份为source+batch_id；对校验后的规范JSON内容计算摘要，普通JSON空白或键顺序变化不造成重复业务处理，事件顺序仍属于批次内容。事件身份为source+event_id。已登记ID不能改写成另一个内容。

接入账本保存“收到/观察过的身份”，每个快照的lineage.json记录“该快照实际已应用的事件”。去重以快照血缘为准：

- 只生成未发布候选后重投，当前快照仍无该事件，继续生成可用候选，避免提前去重丢数据。
- 当前快照已应用时重投，跳过已应用事件，不重复写业务行。
- 回滚到未含事件的版本后重放，可再次补齐同一批事件，结果与原先发布时相同。

这是本地快照内的幂等与重放保证，不是分布式网络端到端exactly-once承诺。跨source使用相同业务主键仍会被业务主键检查拒绝，不能靠换source重复造同一张退款单或首次激活。

## 事务、隔离和中断

每批在复制的候选库中一次事务提交；未知业务引用、重复业务主键、累计超额退款、早于支付日或晚于截止日的事件都会导致整批回滚。当前快照保持不变，失败的原始文件进入隔离区，尝试记录为quarantined。不可直接发布隔离候选。

来源原始文件在data/petkit500/ingestion/archive，异常文件在quarantine；inbox保存本轮模拟输入。标识经过严格校验，不作为SQL代码；表和列由静态处理器选择，业务值使用参数绑定。单实例接入锁防止并行接入相互覆盖。进程崩溃后遗留processing记录在下次接入时标记interrupted，重新投递从快照实际血缘判定是否需要应用；未发布孤立候选不会自动上线。

## 来源与业务数据三方核对

发布前核对批次归档、事件身份账本、快照血缘和实际业务行：每个标记已应用的事件都必须找到一致的来源及退款/激活/绑定/工单/状态/接触记录。空写业务表却只登记血缘、改写业务金额或篡改来源文件均会拒绝验证。

来源归档SHA-256纳入发布凭证，验证后原始批次变化也拒绝发布。原有500表结构、511条关联、订单退款库存一致性、32道独立业务结果和BGE检索门禁继续执行。

接入候选必须基于当前父版本CAS发布；旧分支不能覆盖别人已发布的新数据。普通发布还必须保留当前所有已应用事件及摘要，防止全量刷新静默丢失接入记录。显式历史rollback可退回旧状态，必须明确选择目标并通过原发布门禁。

当前未提供“重建全量基线并自动重放所有上游事件”的工具。接入事件后，单独stage出的无血缘种子库不能直接替换当前业务库；如需重建须先实现或执行经验证的重放迁移流程，不可绕过门禁。事件内容修订、撤销和业务冲正不在v1协议范围，不可用相同event_id改金额。

## 本轮实际演练

未发布候选重复接收后仍成功应用9事件；发布后重投为0事件；内容冲突隔离；“先合法退款、后超额退款”的坏批整批回滚；回滚后同批次再应用9事件，最终业务行及金额与第一次发布完全一致；过期父版本拒绝覆盖。

新版本真实模型的R1销售员工后台问数通过逐型号独立计算核对。32个批准问题均通过，当前228项回归通过（1条Starlette测试客户端弃用提示）。模型验证属于小规模开发验收，不保证任意问题正确。

`scripts/exercise_ingestion.py`会实际添加新模拟事件并发布/回滚/重放，不是只读检查。日常查看使用list和状态API；不要把演练脚本当作无副作用巡检重复运行。

```powershell
.\.venv\Scripts\python.exe scripts/backup_simulated.py --drill
.\.venv\Scripts\python.exe scripts/accept_restored_instance.py
.\.venv\Scripts\python.exe scripts/accept_restored_sources.py
```

恢复副本已实际启动并完成区域任务；又在独立目录校验9个事件的来源归档与业务行、32个业务结果。来源路径重定位到副本的ingestion/archive，不依赖读取原实例归档。原实例没有被覆盖。备份包含业务批次和结果，按业务文件保存，不随仓库分发。
